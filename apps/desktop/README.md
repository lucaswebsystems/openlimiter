# OpenLimiter for the desktop

A window and a tray icon around the engine that already exists. It reads the
same snapshot cache the command line tool writes, applies the same rules, and
puts the provider under the most pressure next to your clock.

Local first, like everything else here. It reads two files and it writes none.
It never touches a credential store, never rewrites a provider's own files, and
opens no network connection at all.

## What it does

- A window showing every provider, its usage, its freshness state, and its
  reset instant, plus the exact block a coding agent would be handed.
- A tray icon beside the clock on Windows, in the menu bar on macOS, and in the
  tray on Linux. Its tooltip carries the provider under the most pressure, and
  on macOS its title carries that percentage as text.
- A tray menu with **Open**, **Refresh** and **Quit**.
- Closing the window hides it rather than quitting, so the tray keeps reading.
  Quit is on the tray menu, and it means quit.

## How the engine gets here

There is one implementation of every rule in this project, and it is the
TypeScript in `packages/`. This application does not have a second one.

`scripts/build-ui.mjs` copies the compiled JavaScript out of
`packages/core/dist`, `packages/connectors/dist` and `packages/adapters/dist`
into `ui/dist/engine`, rewrites the single bare import specifier a bundler
would normally resolve, and copies the three files the window itself is made
of. No bundler, no transpiler, no third party runtime dependency.

Two modules are left out on purpose:

- `core/cache.js` reads a file through node's file system module, which a
  webview does not have. Rust reads those bytes instead and hands them over
  through a command, and the generated barrel supplies a `readSnapshotCache`
  that reports the same missing cache the core reports for an absent file.
- `core/index.js` is the package barrel, which re-exports the module above. A
  barrel generated by the build script takes its place.

Rust does only what Rust has to: resolve the state directory, read
`openlimiter-cache.json` and `manual.json` out of it, and talk to the system
tray. The path convention in `src-tauri/src/state.rs` mirrors
`resolveStateDirectory` in `packages/core/src/cache.ts`, and it moves when that
moves.

## Building it

Rust and the platform's own toolchain are required. Follow the Tauri
prerequisites for your operating system first, then:

```bash
# From the repository root, because the desktop bundle copies the built engine.
pnpm install
pnpm build

cd apps/desktop
pnpm install
pnpm tauri build     # a bundle in src-tauri/target/release/bundle
pnpm tauri dev       # or a development window with the same engine
```

`pnpm tauri dev` and `pnpm tauri build` both run `scripts/build-ui.mjs` first,
so the window always carries the engine as currently compiled. If the packages
have not been built the script says so and stops rather than shipping a stale
copy.

## Icons

`pnpm icons` renders every icon in `src-tauri/icons` from the same approved arc
geometry the website and the favicon use, with no image library involved. It
writes the four PNGs Tauri bundles, three small tray sizes, and a multi size
`icon.ico` for Windows.

It does not write `icon.icns`, which macOS bundling wants and which needs macOS
tooling. On a Mac, one command covers it:

```bash
pnpm tauri icon src-tauri/icons/icon.png
```

## What it deliberately does not do

- No telemetry, no analytics, no crash reporting, no update ping.
- No writing to the state directory. The command line tool owns that file.
- No network. There is no HTTP client in the dependency list.
- No plugin beyond the Tauri core: no file system plugin, no shell, no
  clipboard. The capability file in `src-tauri/capabilities` says so exactly.
